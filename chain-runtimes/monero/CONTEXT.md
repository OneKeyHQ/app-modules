# 交接上下文

写给接手的人（可能没有这个仓库的历史）。**这里只记不能从代码本身读出来的东西。**

## 现在到哪了

Runtime 层扫链闭环 + 花费闭环已通，65 个测试，原生与 wasm32 两个目标零警告，
产物 3.92 MB / gzip 1.22 MB。

**没做的（按优先级）：**

1. **TS / app 层整个没动** —— `sdkMonero`、`Vault`、`Keyring`、四端载体接线。
   Zcash 那边这部分约 6,000 行。这是最大的一块缺口。
2. **硬件签名** —— `OutputWithDecoys` 可序列化，天然支持「准备 / 签名」两阶段，
   但固件协议与 SDK 方法都还没有。
3. **对真实节点的集成测试** —— 现在全是单元测试。扫描循环的三道校验、
   RingCT 索引推算，都只在构造的数据上验证过，没跑过主网。
4. **内存池 / 未确认交易** —— `transactions.height` 允许 NULL 就是给它留的位，
   但没有拉取内存池的路径。
5. **广播重试状态机** —— 广播后立刻记账，但没有「待广播 / 已拒绝」的生命周期
   管理（Zcash 那边是 `tx_state.rs`）。

## 三件必须知道、代码里看不出来的事

**一、扫描进度为什么在 `identities` 而不是从 `blocks` 推。**

`blocks` 表是全局的（块哈希是客观事实，各身份共享）。我一开始拿它的
`max(height)` 当进度，结果是：一个追到链尖的身份会把另一个还在回补的身份的
进度一起推到链尖，那段历史被永久跳过。已修，并有回归测试
`two_identities_keep_independent_progress` 钉住。**别再改回去。**

**二、为什么 `runtime.rs` 没有 wasm-only 门。**

Zcash 那边它是 `#[cfg(target_arch = "wasm32")]`，导致 `runtime.rs` 加两个
`bindgen.rs` 共 1,377 行在原生 `cargo test` 里**根本不编译** —— 那是真实的覆盖
漏洞，我们 review 时才发现。这里刻意不加那个门，所以并发防线（BUSY 守卫、
世代号）是可测的，`runtime.rs` 里那 6 个测试就是。

**三、`cargo check` 不链接。**

给 wasm 目标做验证时只跑 check 会漏掉链接期的问题。本工程踩过一次：
macOS 的 `/usr/bin/ar` 读不懂 wasm 目标文件，把 38 个编译好的 `.o` **静默**
打成 96 字节的空归档，编译阶段零报错，只有 `cargo build` 才暴露。归archiver
已由 `.cargo/config.toml` 固定成 llvm-ar。

## 协议性的硬限制，不是实现问题

**观察钱包检测不到花费。** 需要 key image，而 key image 需要花费私钥。宿主必须
在解锁时调 `importKeyImages`，否则余额偏高。`balance` 返回的
`unverifiableAtomic` 就是这部分，宿主应当据此提示用户。而且补齐只影响**之后**
扫的块 —— 补齐之前发生的花费要回退重扫才认得出来。

**节点声称的 RingCT 输出索引不可验证。** 上游文档明确要求客户端自己维护并比对。
`scan.rs` 实现了独立推算（按本块 v2 交易的输出总数推进游标），不一致报
`RINGCT_INDEX_MISMATCH`。索引错了的后果是构环取错输出、交易被全网拒绝。

**时间戳形式的时间锁判不了。** 只有链高判得了块高形式的锁。时间戳形式的一律
按「仍锁定」处理 —— 让用户等，好过让他构一笔必然被拒的交易。

## 刻意写死、不问节点的三个值

都写死是因为「节点说错了」的后果比「我们发版晚了」严重：

- **环大小 16**（`spend::RING_LEN`）—— 说小了隐私被削弱且可能被拒
- **RctType = ClsagBulletproofPlus** —— 说错了交易被全网拒绝
- **手续费率上限 1,000,000 piconero/weight**（`spend::MAX_FEE_PER_WEIGHT`）
  —— 没上限的话恶意节点报天价费率能让用户把余额全付成手续费

硬分叉时这三个都要跟着改，由我们发版控制。

## 与 Zcash runtime 的重复

只有一处：`crates/monero-runtime/build.rs`（SQLite 的 wasm 链接胶水，与链无关，
实测只差 8 行注释）。现在抽不了 —— 两条链在各自未合并的分支上，没有共同祖先
能放共享 crate。**两条都落 main 之后第一件事就是抽它**，改一边记得同步另一边。

`storage.rs`、`runtime.rs`、`error.rs` 的形状也高度相似但不完全相同，
等 Monero 这边稳定了再决定要不要一起抽 —— 从两个真实实现里抽，
比现在照着一个猜要靠谱。

## 集成测试在本机沙箱里跑不了

`tests/live_node.rs` 对真实节点的那几条，在我的构建沙箱里连不上 —— 已判明是
**沙箱不放行编译出来的测试进程的网络**，不是代码问题：同环境下 `curl` 拿得到
200，而一个五行的裸 `reqwest` 调用同样失败。

所以那几条**没有在真链上跑过**。你那边直接：

```bash
XMR_NODE=http://node.monerodevs.org:18089 \
  cargo test --test live_node -- --nocapture
```

它会打印链尖、扫描速度（块/秒）和余额三档。**扫描速度就是决定整条路线成立
与否的那个数字** —— 单线程扫 Monero 在手机上能不能忍，到今天为止仍然没有答案。
