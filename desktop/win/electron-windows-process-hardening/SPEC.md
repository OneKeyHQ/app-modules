# Windows current-process hardening

## Scope and API

Private local candidate package `@onekeyfe/electron-windows-process-hardening`.
One synchronous `hardenCurrentProcess()` call is available to Node.js or the Electron main process only. It changes the calling Windows process, with no PID, ACL, or policy arguments. Electron renderer and utility processes are rejected. The caller chooses production timing and handles development-mode and opt-out decisions; this package does not install itself or run on import.

The return value has independent `dacl` and `extensionPoint` results. Each result has `status` (`applied`, `failed`, or `unsupported`), and failed results carry `win32Error` when Windows supplied one plus a non-sensitive `message`. Failure in either stage does not prevent attempting the other. On non-Windows systems and unsupported CPU architectures, both results are `unsupported` and no native binary is loaded. Native load failures are represented as two failed results by the JavaScript wrapper.

## Windows behavior

- The DACL stage targets only `GetCurrentProcess()` with `SetSecurityInfo(SE_KERNEL_OBJECT, DACL_SECURITY_INFORMATION | PROTECTED_DACL_SECURITY_INFORMATION)`. The replacement protected DACL starts with an `OWNER RIGHTS` deny `WRITE_DAC` ACE, then allows the current token user and `SYSTEM` exactly `0x00101001`. It does not expose an arbitrary process or ACL API.
- The current user SID comes from the current process token. A temporary SDDL security descriptor is converted to a non-null, present ACL before applying it. Token handles and `LocalFree` allocations are released on all paths; the token-user SID remains valid while used.
- Independently, `SetProcessMitigationPolicy(ProcessExtensionPointDisablePolicy = 6)` receives a four-byte DWORD with `DisableExtensionPoints = 1`.
- `SetSecurityInfo` reports its own DWORD error code. Other Win32 failures use their documented return convention and `GetLastError`. Results never contain the user SID. Native code does not throw for a normal Win32 policy failure.

## Build, tests and boundaries

Windows x64 and ARM64, Node-API 8, Node >=20.17, and the exact Electron/Rust/napi/windows versions from the sibling Windows Hello package and `desktop/release.json`. The source package is private with locked Cargo and npm build dependencies. The build emits architecture-specific `.node` files; the runtime package is dependency-free and has no install script.

Focused tests cover the JavaScript process/platform boundary and independent result behavior. Native tests call hardening only in isolated child processes so the test runner remains unaffected. Node and Electron main-process smoke tests use child processes. Package checks validate both binary architectures and runtime file boundaries. This candidate does not change `desktop/release.json`, desktop publication, consumer dependencies, or other processes. Crashpad integration and crash behavior remain a consumer-level verification concern.

## Test-only local crash prototype

The private candidate also contains an architecture-matched Windows sidecar executable. `startLocalCrashHandler()` is a zero-argument Electron-main API gated by both `DESKTOP_E2E_MODE=true` and `ONEKEY_TEST_LOCAL_CRASH_HANDLER=1`; ordinary production use leaves it disabled. The sidecar path is fixed next to the native binding. Startup failure must not prevent the existing hardening stages.

The sidecar is created through CreateProcessW with protected process DACL 0x00100001 (SYNCHRONIZE, TERMINATE; no QLI) and protected initial-thread DACL 0x00100800 (SYNCHRONIZE, QUERY_LIMITED_INFORMATION). Its initial thread remains suspended until assignment to a helper-only kill-on-close job. The creation handle has PROCESS_DUP_HANDLE but lacks WRITE_DAC under the initial DACL. Before either creation gate, the parent uses it to duplicate the child's pseudo process handle into a parent-only, non-inheritable READ_CONTROL|WRITE_DAC (0x00060000) control handle, verifies that it names the created helper, and uses it only for the final process DACL transition. Before resume, the parent verifies a distinct child TokenId, sets the child TokenDefaultDacl to the 0x00100800 ACL for later-created objects, restricts the child token object DACL to TOKEN_QUERY for the current user and SYSTEM with OWNER RIGHTS denying WRITE_DAC, verifies both child ACLs and that the parent token default DACL is unchanged, then updates only the helper process DACL to final 0x00101001 and closes the control handle before the final gate. Each failure terminates the helper and disables the collector for that start. This control-handle behavior has been exercised on the current Windows 11 x64 host; other Windows versions remain unverified and the collector remains test-only. STARTUPINFOEXW inherits only the three listed standard I/O handles; returned process and thread handles are non-inheritable. After the helper confirms its PID and protocol, the parent duplicates a non-inheritable target handle with exactly 0x00120410 (SYNCHRONIZE, READ_CONTROL, PROCESS_QUERY_INFORMATION, PROCESS_VM_READ). Main-process DACL hardening completes before the sidecar is created and its ready acknowledgment is received. On Electron 44.5.1 x64 only, startup resolves the fixed `V8::SetUnhandledExceptionCallback` export in the main executable and registers through a C++ bridge checked against the exact official V8 headers. Its fatal callback sends target-side `ExceptionInformation` (exception pointers and thread ID) through private, parent-overlapped named pipes with a 30-second absolute deadline, waits for capture acknowledgment, then terminates the crashing process. A Windows unhandled-exception filter covers paths that reach it, but Electron's `process.crash()` is intercepted earlier by V8. The V8 C++ export is not a stable Node-API contract; other Electron versions and ARM64 are unsupported for this prototype. This prototype does not claim FailFast, abort, hang, or arbitrary first-chance coverage.

The handler uses a preauthorized process handle and a pinned standalone Crashpad snapshot/minidump writer to capture into a bounded 128 MiB memory buffer. A local patch to Crashpad revision ad1827ddbc03f1c214030b31b380243ded660b95 reads only the fault thread saved exception CONTEXT; this capture path suspends neither the target process nor any target thread. Other threads are omitted and the handle stream is empty. The verified PE runtime-function directory is capped at 16 MiB, consists of complete 12-byte entries, and must stay within the image; Electron 44.5.1 uses about 5.3 MiB. It never sets a NULL target DACL and has no DbgHelp dump fallback. It compares the target DACL bytes and protection state before and after capture, then rebuilds a new JSON object from validated Exception, ThreadList, and ModuleList streams. `StackWalkEx` callbacks read captured thread stacks and only executable code plus read-only `.pdata`/`.xdata`/`.rdata` from locally mapped, identity-matched PE files; Windows PE unwind records can reside in `.rdata`. They never read live target memory or consult symbol servers. The fault thread uses the ExceptionStream context and its captured ThreadList stack. Other threads are not captured. The fault thread must have its context frame and at least one further frame or sanitization fails. Each frame contains only an allowed module ID, module-relative offset, and a `context`, `stackwalk`, or `leaf_stack` source label. On x64 only, verified executable code with no runtime-function entry uses the documented leaf return: read exactly one aligned [RSP] slot from the captured stack, advance RSP by 8, and require a return PC in verified executable code; it never scans for a candidate. A function-table callback hit alone does not prove DbgHelp's internal unwind choice; known-chain testing independently checks frame order. The report also contains schema, epoch time, validated app version, exception code, top module ID/offset, `captureBackend`, `daclUnchanged`, and bounded thread/frame arrays. Unknown modules do not acquire paths or symbols from the dump.

The raw minidump is neither written to disk nor uploaded. Capture, ACL verification, parsing, unwind, and write failures produce no `report.json`; sanitized JSON is written and synced to `report.pending` before rename to `report.json`. A separate fixed-stage `status.json` contains no dump data. Output is limited to a newly created `local-crash-prototype` directory under the empty test profile. This is a local JSON prototype, not a sanitized minidump or a claim about Electron Crashpad's separate files. The fault callback allows 30 seconds for capture acknowledgment and then terminates its own already-crashed process. The helper-only job closes with the parent and kills an orphan helper; the sidecar exits immediately after acknowledgment. The 35-second total-exit requirement awaits fault-injection verification. The double test gate remains. A fixed test-only fault hook can publish a `mode:suspend` marker then freeze only the helper itself through ntdll `NtCreateProcessStateChange` and `NtChangeProcessState` with `GetCurrentProcess()`. The unnamed, non-inheritable state object requests only access 0x1 and uses the unchanged narrow token default DACL; its handle stays open until helper termination so later threads remain frozen. Missing exports or a failed call produce `suspend_failed`, with no one-shot suspension fallback. A same-ACL isolated helper component verified both existing and subsequently created threads at State 5 / SuspendCount 1 for 35 seconds. This remains separate from the production capture DLL, which never suspends the target; capture deadlines, exit logic, and every ACL are unchanged. The marker alone does not prove suspension; system thread snapshots and the 35-second exit/orphan checks are required. The previous helper's same-user probe confirmed `PROCESS_QUERY_LIMITED_INFORMATION`, then `OpenProcessToken` with `TOKEN_ADJUST_DEFAULT` and `WRITE_DAC`; this motivated the new suspended-start token transition. Two test-only creation gates sample the initial no-QLI state and the final token/process/thread rights before the first helper instruction. On the current Windows 11 x64 host, both pre-resume creation gates passed the process, initial-thread, and token-access assertions for their respective states. The pre-detached candidate exited before Rust entry with 0xC0000142 (DLL_INIT_FAILED) after resume. A six-case fixed-helper component probe reproduced this failure in every case that set TokenDefaultDacl to 0x00100800; the baseline, token-object-DACL-only, and token-object-DACL plus final-process-DACL cases reached Rust entry and exited on stdin EOF. Matching Microsoft public symbols and process-local loader snaps identified ntdll!NtDeviceIoControlFile, called by KERNELBASE!ConsoleLaunchServerProcess with ConDrv IOCTL 0x00500037, returning ACCESS_DENIED under the narrow TokenDefaultDacl. Helper creation now uses DETACHED_PROCESS instead of CREATE_NO_WINDOW to avoid implicit console allocation, retaining CREATE_SUSPENDED, the explicit standard-handle allowlist, the job, and every process/thread/token ACL. The isolated component reaches Rust entry with the full ACL combination. The rebuilt candidate also passes real production-main startup/IPC, both pre-resume rights gates, normal and known-chain crash capture, output-file reopen/restart, and injected capture/scrub/unwind failure behavior under an empty test profile. Runtime helper thread and token probes pass with no dangerous rights, but Phase A acceptance remains incomplete: ordinary-token system handle inventory returns ACCESS_DENIED, and a concurrent hang-scrub test observed 35.971 seconds from fixture trigger timestamp to main exit. An isolated rerun measured 30.072 seconds; the concurrent delay is unresolved, and the trigger timestamp precedes fixture metrics collection/file writing. The earlier suspend-read and suspend-unwind failures were traced to NtSuspendProcess leaving later WorkerFactory threads unfrozen (SuspendCount 0); wait reason alone cannot establish suspension. The state-change test hook above fixes this gap. The final freeze candidate passes suspend-read, suspend-unwind, and hang-scrub targeted behavior checks, including a verified restart/other-case exit overlap; all completed exits remain within 35 seconds and both suspension cases confirm positive counts for every thread. Two additional attempts stopped before crash injection because of a terminated-thread probe race and watcher startup timeout; these are retained as incomplete observations, with no verifier changes. The pre-freeze candidate recorded 21 completed behavior cases and six incomplete cases; its full matrix has not been rerun and full Phase A acceptance remains incomplete. Collector startup fails closed and ordinary production use remains disabled. The narrow token default DACL affects all new helper objects; fixed `status.json`, `fault-stage.json`, and `report.pending` files therefore receive an explicit file DACL granting the current user and SYSTEM read/write/delete without widening the token default.

The fixed Electron 44.5.1 x64 V8 callback is registered through a small C++ bridge compiled against the exact official Electron headers. A local prototype build requires `ONEKEY_CRASHPAD_CAPTURE_DLL` pointing to an x64 DLL with the adjacent receipt produced by `scripts/build-capture.ps1`. `scripts/build.mjs` and `scripts/check-package.mjs` verify the fixed Crashpad source, dependency, patch, wrapper and tool identities recorded in that receipt against the current source, and verify the actual DLL checksum and PE architecture. This local receipt records a build; it is not a signed provenance proof or a promise of byte-identical builds on other machines. The build downloads or reuses the exact official Electron 44.5.1 headers archive after verifying its pinned SHA-256, and compiles the bridge only with the verified `v8.h`. The DLL is copied to a fixed adjacent runtime name; no runtime environment path is accepted. A normal build without this explicit local input leaves hardening available but fails closed at crash-handler startup. The wrapper source and third-party licenses are in this package; rebuilding the DLL uses the pinned external Crashpad revision `ad1827ddbc03f1c214030b31b380243ded660b95`, its DEPS, the local fault-only patch, and its GN/Clang toolchain. `triggerLocalCrashForTest()` is a zero-argument, same-gated test entry that creates a real PAGE_NOACCESS access violation through three non-inlined native calls. It has no PID, address, or output-path arguments and is unavailable in ordinary production use. Its PDB stays local and is not packaged.

The 2026-10-22 closeout rebuilt a new private capture and x64 candidate from those pinned inputs. The x64 candidate build receipt binds the bridge-enabled `.node`, helper, capture DLL, and exact Electron headers; `prepack` rejects a subsequent plain x64 build even when an old capture DLL remains. Six focused harness cases completed their intended behavior within the existing 30-second native and 35-second kernel/signal gates; the exact candidate hashes and timings are recorded in `README.md`. Phase A remains incomplete because ordinary-account inherited-handle inventory reported `target QLI anchor/layout invalid` in those runs. The older `ACCESS_DENIED` inventory result and 35.971-second concurrent observation above describe prior attempts, not these six closeout runs. The verified scope remains the helper's new high-risk process opens; main-process thread/token rights and the `CreateProcess`-to-`AssignJob` interval remain outside the proven boundary.
